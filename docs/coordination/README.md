# FE·BE 협업 메시지

프론트엔드와 백엔드 세션 사이의 계약 질문, 답변, 결정 사항을 순서대로 남기는 공간이다.
채팅 전문을 복사하기보다 **상대가 행동하거나 결정해야 하는 내용**만 한 메시지에 담는다.

> **세션 시작 지침:** FE나 BE 세션이 이 폴더를 처음 전달받았다면, 먼저 이 문서를 끝까지 읽고
> `열린 스레드`에서 자신이 `다음 담당`인 메시지를 확인한다. 채팅으로만 답하지 말고 아래 규칙에
> 따라 응답 파일을 남긴다.

## 대화 흐름

```text
보내는 세션
  → 새 메시지 파일 생성
  → README의 열린 스레드에 최신 메시지·다음 담당 기록

받는 세션
  → README와 자신에게 온 최신 메시지 확인
  → 열린 스레드 상태를 IN_PROGRESS로 변경
  → 필요한 조사·코드 작업 수행
  → 새 reply 파일 생성(reply_to로 원문 연결)
  → README의 최신 메시지·다음 담당·상태 갱신

합의 완료
  → 실제 기준 문서와 코드에 결정 반영
  → 열린 스레드에서 닫힌 스레드로 이동
```

메시지 파일은 알림과 의사결정 기록이고, 최종 계약의 원본은 `docs/api_contract.md` 같은 기준
문서다. 메시지에서 합의만 하고 기준 문서를 갱신하지 않은 상태는 완료로 보지 않는다.

## 사용 규칙

1. 작업 시작 전에 아래 `열린 스레드`와 관련 스레드의 최신 메시지를 읽는다.
2. 메시지는 `messages/CNNNN_FROM_to_TO_slug.md` 형식으로 만든다.
   - 예: `C0001_FE_to_BE_study_contract_sync.md`
   - `FROM`과 `TO`는 `FE`, `BE`, `ALL` 중 하나를 사용한다.
3. 새 파일을 만들기 직전에 `messages/`의 가장 큰 번호를 확인하고 다음 번호를 사용한다.
   번호가 충돌하면 기존 파일을 수정하지 말고 그 다음 번호를 사용한다.
4. 보낸 메시지 본문은 기록 보존을 위해 원칙적으로 수정하지 않는다. 정정은 새 메시지로 남긴다.
5. 답변도 새 파일로 만들고 frontmatter의 `thread_id`와 `reply_to`로 원문을 연결한다.
6. 현재 상태와 다음 행동은 이 파일의 `열린 스레드` 표만 갱신한다.
7. 계약이 확정되면 실제 기준 문서(`docs/api_contract.md` 등)를 수정하고 스레드를 `CLOSED`로 옮긴다.
8. 상대 질문에 일부만 답할 경우 누락 항목을 `남은 질문`에 명시하고 상태를 `OPEN` 또는
   `BLOCKED`로 유지한다.

## 받는 세션의 응답 체크리스트

- `to`가 자신의 역할인지 확인한다.
- `related` 문서와 코드를 실측한다.
- 질문별로 `결정 / 구현 완료 / 미구현 / 차단 사유`를 구분한다.
- 실행한 테스트와 결과를 적는다.
- 새 파일의 `reply_to`에 받은 메시지 ID를 적는다.
- README의 열린 스레드 표를 새 응답 파일 기준으로 갱신한다.
- 상대 세션의 추가 작업이 필요하면 `다음 담당`을 상대 역할로 바꾼다.

## 상태

- `OPEN`: 상대 세션의 답변이나 작업이 필요함
- `IN_PROGRESS`: 담당 세션이 작업 중
- `BLOCKED`: 외부 결정이나 선행 작업이 필요함
- `CLOSED`: 합의가 기준 문서와 코드에 반영됨

## 최신 메시지 확인

파일명은 번호순으로 정렬되므로 `messages/`에서 번호가 가장 큰 파일이 전체 최신 메시지다.
다만 여러 스레드가 동시에 진행될 수 있으므로 **최신 파일 하나만 읽지 말고 열린 스레드 표의 최신
메시지도 함께 확인한다.**
